## B5 [medium] With 'empty first', deletes run before any export or destination preflight, and a delete that 404s fails permanently
**Where:** src/server/jobs/runner.ts:175 (+ src/server/jobs/planner.ts)  
**Status:** fixed

**Change:** planner.ts (~lines 48-58 and the per-doc loop): export steps for docs without a same-name destination keeper are now pushed before the delete steps (with a comment), and removed from the per-doc import/models/verify/meta group. runner.ts runDestination (~lines 210-230, 245-259, 423): added exportFailed and a lazily cached deleteBlockReason(). It blocks deletes if any export in this destination failed, or if this destination has import steps and ensureTarget() throws (wrong or unreadable destination model). A blocked delete is recorded as skipped with 'not deleted: ...' and the loop continues. A delete that returns OmniError 404 is now treated as success with the note 'already deleted'; the 404 tolerance lives in the runner, so OmniClient.deleteDoc and scripts/delete-doc.ts still report a 404. The catch block sets exportFailed when an export item fails. README.md (Document Migrator bullet) and docs/in-place-update-test-plan.md (new cases D4 and D5) updated to match.

**Follow-up:** Both reviewer points were real. (1) skip() stores and streams its note unclipped, and the delete-block note embedded the raw OmniError message (full response body), repeated on every blocked delete row. (2) modelBlock is cached for the whole run while target is not, so a transient getModel failure at the first delete skipped every delete, a later import's ensureTarget() could then succeed, and since 'skipped' counts as success in computeStatus (and Retry only re-runs failed items) the job could end 'succeeded' with the folder never emptied. Fix: the embedded model error is now clipped to 500 chars (clip(..., 500)), and blocked deletes now go through fail() instead of skip(), so the stored/streamed note is also bounded by fail()'s 4000-char clip, the job ends partial/failed rather than succeeded, and Retry re-runs the deletes (RETRYABLE_ITEM_KINDS includes 'delete'; retry already orders exports, then deletes, then the rest). fail() is used for both block reasons (export failed and model unusable) because the same skipped-counts-as-success / Retry-ignores-skipped problem applies; in the export-failed case the job was already not 'succeeded', but Retry could never empty the folder afterwards. skip() itself is unchanged (its remaining callers pass fixed or short notes). README.md line 17 and docs/in-place-update-test-plan.md D4 updated to describe failed (not skipped) blocked deletes.

**Behaviour change:** Plan preview and Job Detail now list all export steps first, then deletes, then the per-document update or import/models/verify/meta steps. If an export fails, or the destination model can't be read (wrong Base Model ID) while there are imports to run, the delete steps are skipped and the destination folder (and its schedules) is left as it was. A delete whose document is already gone succeeds with the note 'already deleted' instead of failing permanently. Same-name duplicate cleanup uses the same gate.

**How to test:** 1. Preview with 'Empty each destination folder' ticked and a destination that has an unrelated dashboard: the plan lists the export step(s) before the delete step(s).
2. Wrong destination model: use a destination whose Base Model ID is wrong, tick 'Empty each destination folder' and run. Exports succeed; the delete rows are skipped with 'not deleted: destination model unusable (...)'; import and the steps after it fail with 'not run: import failed...'; the destination folder still contains its original dashboards.
3. Failed export: make a source export fail (for example delete the picked dashboard in the source after the preview, or use an invalid source key) with 'Empty each destination folder' ticked. The export fails, the delete rows are skipped with 'not deleted: an export step failed...', and nothing is deleted at the destination.
4. Already-deleted doc: preview with 'Empty each destination folder' ticked, delete one of the listed destination dashboards by hand in Omni, then run. That delete row succeeds with the note 'already deleted' and the job reaches 'succeeded'.
5. Happy path: a normal run with 'Empty each destination folder' ticked deletes the unrelated dashboards, imports new ones and updates matching ones in place as before.
